# DN42 Search 架构设计文档

## 1. 设计目标

为 dn42 去中心化网络构建一个轻量级、高性能的搜索引擎，
借鉴 Google 搜索引擎的核心技术，同时适配 dn42 网络的特点。

### 1.1 设计原则

1. **轻量级**：单服务器即可部署，资源占用低
2. **正确性**：严格限制在 dn42 网络范围内，尊重 robots.txt
3. **可扩展**：模块化设计，支持分布式扩展
4. **教育性**：代码结构清晰，便于学习搜索引擎原理
5. **去中心化精神**：支持 P2P 架构演进

### 1.2 性能目标

- 单节点支持 100 万页面索引
- 查询响应 < 100ms
- 爬虫速率 10-50 pages/s（取决于网络）
- 索引构建速度 1000+ pages/s

## 3. 核心模块设计

### 3.1 爬虫模块

#### 3.1.1 URL Frontier 架构

采用 Mercator 论文中的双队列架构：

```
                    ┌─────────────────────┐
                    │   前端优先级队列     │
                    │  (Priority Bands)   │
                    └──────────┬──────────┘
                               │ 路由器（加权选择）
                               ▼
                    ┌─────────────────────┐
                    │   后端主机队列       │
                    │  (Per-host Queues)  │
                    │  Host A: [url1,url2]│
                    │  Host B: [url3]     │
                    │  Host C: [...]      │
                    └─────────────────────┘
```

**设计要点**：
- 前端队列：按优先级分带（高/中/低），全局 BFS 遍历
- 后端队列：每主机一个队列，保证礼貌性
- 路由器：按加权概率从各优先级带选择 URL，分配到对应主机队列

#### 3.1.2 礼貌性策略

1. **每主机并发限制**：默认 3 个并发请求
2. **请求间隔**：默认 1 秒，可被 robots.txt 覆盖
3. **Robots.txt 遵守**：支持 User-agent、Disallow、Crawl-delay
4. **指数退避重试**：失败后延迟重试，最多 3 次

#### 3.1.3 去重策略

- **URL 去重**：规范化后 SHA-256 哈希 + 集合存储
- **内容去重**：SHA-256 哈希精确去重
- **近邻去重**：预留 SimHash 接口

### 3.2 倒排索引模块

#### 3.2.1 数据结构

```
词典 (Dictionary):
  term -> {df, offset, size}

倒排列表 (Postings):
  term -> [
    {doc_id, freq, positions, fields},
    {doc_id, freq, positions, fields},
    ...
  ]

文档元数据 (DocInfo):
  doc_id -> {url, title, length, pagerank}
```

#### 3.2.2 索引压缩

使用可变字节编码（Variable Byte Encoding）：

```
整数 135 的编码：
135 = 10000111 (二进制)
→ 00000011 00001110 (两个字节)
  第一个字节: 高位7位 + 续位标记=1
  第二个字节: 低位7位 + 续位标记=0
```

**压缩效果**：
- 小整数（< 128）：1 字节，节省 75%
- 中等整数（< 16384）：2 字节，节省 50%
- 大整数：3-5 字节，节省 ~50%

#### 3.2.3 字段加权

支持多字段索引，各字段权重可配置：

| 字段 | 默认权重 | 说明 |
|------|----------|------|
| title | 5.0 | 页面标题 |
| url | 3.0 | URL 路径 |
| headings | 2.0 | h1-h3 标题 |
| body | 1.0 | 正文内容 |
| anchor | 2.5 | 锚文本 |

### 3.3 排序模块

#### 3.3.1 BM25 算法

完整实现 Okapi BM25：

```python
def score(query_terms, doc_id):
    score = 0
    for term in query_terms:
        idf = log((N - df + 0.5) / (df + 0.5) + 1)
        tf = get_tf(term, doc_id)
        numerator = tf * (k1 + 1)
        denominator = tf + k1 * (1 - b + b * doc_len / avgdl)
        score += idf * numerator / denominator
    return score
```

**参数选择依据**：
- `k1 = 1.5`：平衡词频权重，防止关键词堆砌
- `b = 0.75`：适度的文档长度归一化

#### 3.3.2 PageRank 算法

幂迭代法实现：

```python
def compute(links, N, d=0.85, tol=1e-6):
    PR = {p: 1/N for p in pages}
    
    for iteration in range(max_iterations):
        new_PR = {}
        dangling_sum = sum(PR[p] for p in dangling_nodes)
        
        for p in pages:
            rank_sum = sum(PR[in_p] / out_degree(in_p) 
                          for in_p in in_links[p])
            new_PR[p] = (1-d)/N + d * (rank_sum + dangling_sum/N)
        
        if max_diff(new_PR, PR) < tol:
            break
        PR = new_PR
    
    return PR
```

**收敛特性**：
- 通常 50-100 次迭代收敛
- 时间复杂度：O(iterations * E)，E 为边数
- 空间复杂度：O(N + E)

#### 3.3.3 混合排序

综合 BM25 相关性和 PageRank 权威度：

```
final_score = w_bm25 * normalized_bm25 + w_pagerank * normalized_pagerank
```

默认权重：
- BM25: 0.7
- PageRank: 0.3

### 3.4 查询处理模块

#### 3.4.1 拼写检查器

基于 Peter Norvig 的经典算法：

1. 生成编辑距离 1 的所有候选（~54n+25 个）
2. 生成编辑距离 2 的候选（仅当编辑距离 1 没有匹配时）
3. 基于词频语言模型选择最可能的修正

#### 3.4.2 查询意图分类

简单规则分类：
- **导航型**：包含 site, official, homepage 等词
- **事务型**：包含 download, buy, login 等词
- **信息型**：默认

## 4. 数据流

### 4.1 爬取流程

```
种子 URL
   ↓
URL Frontier（优先级队列）
   ↓
下载器（aiohttp 异步）
   ↓
内容解析（BeautifulSoup）
   ├─→ 提取文本 → 存入数据库
   ├─→ 提取链接 → 去重 → 加入 Frontier
   └─→ 元数据 → 存入数据库
```

### 4.2 索引构建流程

```
页面文本
   ↓
分词（Tokenizer）
   ↓
词频统计（考虑字段权重）
   ↓
写入倒排索引（内存）
   ↓
（缓冲区满时）刷新到磁盘
   ↓
段合并（后台线程）
```

### 4.3 搜索流程

```
用户查询
   ↓
查询解析（分词、过滤、提取操作符）
   ↓
拼写检查 → 建议修正
   ↓
倒排索引查询 → 获取匹配文档
   ↓
BM25 评分
   ↓
PageRank 加权
   ↓
综合排序
   ↓
生成摘要和高亮
   ↓
返回结果
```

## 5. 持久化格式

### 5.1 索引文件

```
data/index/
├── index_meta.json      # 元数据（文档数、平均长度、版本）
├── dictionary.json      # 词典（词项 -> df, offset, size）
├── postings.bin         # 倒排列表（二进制）
└── doc_info.json        # 文档元数据
```

### 5.2 倒排列表二进制格式

```
[doc_count: varint]
[doc_id_len: varint][doc_id: bytes][freq: varint][pos_count: varint][positions: varint...]
[doc_id_len: varint][doc_id: bytes][freq: varint][pos_count: varint][positions: varint...]
...
```

### 5.3 数据库表

- `pages`：页面元数据
- `url_queue`：URL 爬取队列
- `links`：链接关系（用于 PageRank）
- `index_status`：索引状态

## 6. 性能分析

### 6.1 时间复杂度

| 操作 | 时间复杂度 | 说明 |
|------|-----------|------|
| 文档索引 | O(L) | L 为文档长度 |
| 单词查询 | O(DF) | DF 为文档频率 |
| 多词查询 | O(min(DF_i)) | 最短倒排列表驱动 |
| BM25 评分 | O(K) | K 为查询词数 |
| PageRank 计算 | O(I * E) | I 为迭代次数，E 为边数 |

### 6.2 空间复杂度

| 数据结构 | 空间复杂度 | 说明 |
|----------|-----------|------|
| 倒排索引 | O(T * avg_postings) | T 为词项数 |
| 词典 | O(T) | |
| 文档元数据 | O(N) | N 为文档数 |
| 链接图 | O(E) | E 为边数 |

### 6.3 预期性能（单节点）

| 指标 | 估计值 | 说明 |
|------|--------|------|
| 爬取速率 | 10-50 pages/s | 取决于网络带宽和目标站点速度 |
| 索引构建 | 500-2000 pages/s | 取决于文档长度 |
| 查询延迟 | 10-100ms | 取决于词项频率和结果集大小 |
| 10 万页面内存 | ~500MB | 索引 + 元数据 |
| 100 万页面内存 | ~3-5GB | 索引 + 元数据 |

## 7. 分布式扩展方案

### 7.1 爬虫分布式

**方案：主从架构 + 任务队列**

```
调度节点 (Master):
  - 维护全局 URL 队列
  - 分配任务给 Worker
  - 收集结果

工作节点 (Worker):
  - 执行实际爬取
  - 解析页面
  - 上报新 URL
```

**技术选型**：
- 任务队列：Redis / RabbitMQ
- 结果存储：共享数据库 / 分布式存储

### 7.2 索引分布式

**方案：按文档分片**

```
查询请求
   ↓
协调节点（Coordinator）
   ├─→ 分片 1 → 本地 Top K 结果
   ├─→ 分片 2 → 本地 Top K 结果
   ├─→ 分片 3 → 本地 Top K 结果
   └─→ ...
   ↓
聚合全局 Top K
   ↓
返回结果
```

**分片策略**：
- 按 doc_id 哈希分片
- 每个分片是完整的倒排索引子集
- 查询必须扇出到所有分片

### 7.3 P2P 架构（远期）

参考 YaCy 的 P2P 设计：

- 节点发现：种子节点 + Gossip 协议
- 分布式索引：DHT 分片存储
- 分布式搜索：广播查询 + 结果聚合
- 信誉系统：防止恶意节点返回虚假结果
